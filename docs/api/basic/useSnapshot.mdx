# `useSnapshot`

Create a local tracked snapshot that catches changes.

Normally, Valtio's snapshots (created via <a href="/docs/api/advanced/snapshot">`snapshot()`</a>) are recreated on _any_ change to a proxy, or any of its child proxies.

However `useSnapshot` wraps the Valtio snapshot in an access-tracking proxy. This is to make sure your component is render optimized, i.e. it will only re-render if keys that it (or its child components) specifically accessed has changed, and not on every single change to the proxy.

We call this a tracked snapshot and name it `tracked` in examples. `state`
refers to the mutable proxy, and `snap` refers to a vanilla snapshot returned
by `snapshot(state)`.

## Usage

### Read from snapshots in render, use the proxy in callbacks

Snapshots are read-only to render the JSX from their consistent view of the data.

Mutations, and also any reads in callbacks that make mutations, need to be made via the proxy, so that the callback reads & writes the latest value.

```jsx
function Counter() {
  const tracked = useSnapshot(state)
  return (
    <div>
      {tracked.count}
      <button
        onClick={() => {
          // also read from the state proxy in callbacks
          if (state.count < 10) {
            ++state.count
          }
        }}
      >
        +1
      </button>
    </div>
  )
}
```

### Copying snapshot data into state

Do not assign the access-tracking objects returned by `useSnapshot` directly
to mutable state. Use `deepClone` to copy their data first:

```jsx
import { deepClone } from 'valtio/utils'

function CopyButton() {
  const tracked = useSnapshot(state)
  return (
    <button
      onClick={() => {
        destination.child = deepClone(tracked.child)
      }}
    >
      Copy
    </button>
  )
}
```

This copies the rendered version, not necessarily the latest state. Clone
the whole payload if it contains nested read snapshots. The clone's reads
are tracked, but later operations on the copied data are not; `ref` values
remain shared. Direct assignment is unsupported and is not rejected at
runtime.

### Parent/Child Components

If you have a parent component use `useSnapshot`, it can pass snapshots to child components and the parent & children will re-render when the snapshot changes.

For example:

```jsx
const state = proxy({
  books: [
    { id: 1, title: 'b1' },
    { id: 2, title: 'b2' },
  ],
})

function AuthorView() {
  const tracked = useSnapshot(state)
  return (
    <div>
      {tracked.books.map((book) => (
        <Book key={book.id} book={book} />
      ))}
    </div>
  )
}

function BookView({ book }) {
  // book is a tracked snapshot
  return <div>{book.title}</div>
}
```

If book 2's title is changed, a new `tracked` is created and the `AuthorView` and `BookView` components will re-render.

Note if `BookView` is `React.memo`d, the 1st `BookView` will not re-render, b/c the 1st `Book` snapshot will be the same instance, as only the 2nd `Book` was mutated (the root `Author` snapshot will also be updated since the list of `books` has changed).

### Child Components Making Mutations

The above approach works if `BookView` is read-only; if your child component needs to make mutations, then you'll need to pass the proxy:

```jsx
function AuthorView() {
  const tracked = useSnapshot(state)
  return (
    <div>
      {tracked.books.map((book, i) => (
        <Book key={book.id} book={state.books[i]} />
      ))}
    </div>
  )
}

function BookView({ book }) {
  // book is the proxy, so we can track it and mutate it
  const tracked = useSnapshot(book)
  return <div onClick={() => book.updateTitle()}>{tracked.title}</div>
}
```

Or you can pass both the snapshot and proxy together, if you don't want to call `useSnapshot` in the child component:

```jsx
function AuthorView() {
  const tracked = useSnapshot(state)
  return (
    <div>
      {tracked.books.map((book, i) => (
        <Book key={book.id} bookProxy={state.books[i]} trackedBook={book} />
      ))}
    </div>
  )
}
```

There should be no performance difference between these two approaches.

### Read only what you need

Every object inside your proxy also becomes a proxy (if you don't use <a href="/docs/advanced/ref">`ref()`</a>). So you can also use them to create
a local snapshot.

```jsx
function ProfileName() {
  const tracked = useSnapshot(state.profile)
  return <div>{tracked.name}</div>
}
```

## Gotchas

Subscriptions are attached directly to the proxy that owns an accessed key.
Reading `tracked.profile.name` subscribes to `name` on `state.profile`.
Replacing or deleting `state.profile` also invalidates these subscribers,
so the component follows the new value:

```js
const previous = state.profile
state.profile = { name: 'new name' }

state.profile === previous // false
```

Replacing a child can cause a render even when the used leaves are equal.
Use direct leaf updates or [`applyChanges`](../utils/applyChanges.mdx) to
update compatible ordinary objects and arrays in place.

Reading an object or array without reading its properties observes its entire
subtree. For example, `useEffect(effect, [tracked.profile])` reacts to changes
anywhere inside `profile`. Nested property reads narrow that tracking.

Use `trackKey` to retain whole-container tracking alongside nested reads:

```js
const tracked = useSnapshot(state)
const profile = trackKey(tracked, 'profile')
profile.name
```

Now changes to unread descendants also trigger a render because the
`profile` snapshot identity changes. Leaf-key subscriptions have O(1)
registration; container subscriptions recursively observe their descendants.
Calling `useSnapshot(state)` without using its result does not subscribe.

Getters execute on every access, using the render snapshot as `this`.
`useSnapshot` subscribes to the keys read by the getter, without caching or
comparing its result:

```js
const state = proxy({
  count: 0,
  get selected() {
    return { value: this.count % 2 }
  },
})

function Component() {
  const tracked = useSnapshot(state)
  return <div>{tracked.selected.value}</div>
}
```

Changing `count` from `0` to `2` re-renders `Component` because the accessed
`count` key changed. This also applies when a getter returns a primitive with
the same value. See the [v3 migration guide](../../guides/migrating-to-v3.mdx)
for explicit memoization with `proxy-memoize` and the `valtio-reactive`
migration path for managed computed state.

{/* TODO: Document valtio-reactive computed as a mitigation after v3 support. */}

Functions are passed through unchanged. Reading a function-valued key tracks
that key, but calling it does not automatically track state read through
closures. This applies to stored functions and functions returned by getters.
If a getter returns a closure capturing `this`, accessing it through `tracked`
captures the render snapshot, so subsequent reads through that receiver can
also subscribe.

A method called through the render snapshot can track reads through `this`:

```js
const state = proxy({
  count: 0,
  select() {
    return this.count
  },
})

function Component() {
  const tracked = useSnapshot(state)
  return <div>{tracked.select()}</div>
}
```

Here `this` is `tracked`, so reading `this.count` subscribes to `count`.
